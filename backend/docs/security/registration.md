# Політика безпеки та моніторингу реєстрації

Цей документ описує заходи безпеки, впроваджені для захисту ендпоінтів реєстрації, а також процедури моніторингу та реагування на підозрілу активність.

## 1. Впроваджені заходи безпеки

Для захисту від автоматизованих атак (ботів) та спаму використовуються наступні механізми:

### 1.1. Google reCAPTCHA v2

- **Опис:** Користувач повинен пройти перевірку "Я не робот" перед відправкою форми реєстрації.
- **Реалізація:**
    - **Frontend:** Компонент `ReCAPTCHA` інтегрований у форми реєстрації.
    - **Backend:** Токен, отриманий від Google, валідується на стороні сервера за допомогою `drf-recaptcha` у `RegistrationSerializer`.

### 1.2. Обмеження частоти запитів (Throttling)

Для запобігання brute-force атак та спаму застосовуються два рівні троттлінгу:

1.  **За IP-адресою (`CommonRedisThrottle`):**
    - **Ліміт:** 5 запитів на хвилину з однієї IP-адреси.
    - **Призначення:** Захист від атак з одного джерела.

2.  **За Email-адресою (`EmailThrottle`):**
    - **Ліміт:** 6 запитів на годину для однієї email-адреси.
    - **Призначення:** Запобігання спаму та багаторазовим спробам реєстрації одного й того ж акаунту, навіть з різних IP.

Ці обмеження застосовуються до ендпоінтів реєстрації (`/api/auth/register/`) та скидання пароля.

## 2. Моніторинг та сповіщення

Для своєчасного виявлення аномальної активності необхідно відстежувати наступні показники.

### 2.1. Сплески кількості реєстрацій

- **Як виявити:** Регулярно виконувати SQL-запит для підрахунку нових користувачів за певний проміжок часу.
  ```sql
  -- Підрахунок нових користувачів за останню годину
  SELECT COUNT(*) FROM users_user WHERE date_joined > NOW() - INTERVAL '1 hour';
  ```
- **Сповіщення:** Налаштувати автоматизований скрипт (cron job) або інструмент моніторингу (напр., Grafana, Datadog), який виконує цей запит і надсилає сповіщення (наприклад, у Slack або на email), якщо кількість перевищує встановлений поріг (напр., >50 реєстрацій за годину).

### 2.2. Високий відсоток відмов email-повідомлень (Bounce Rate)

- **Як виявити:** Цей показник відстежується через панель керування вашого email-провайдера (напр., SendGrid, Mailgun, AWS SES). Високий відсоток відмов може свідчити про реєстрацію на неіснуючі адреси.
- **Сповіщення:** Налаштувати сповіщення безпосередньо в сервісі email-провайдера, коли відсоток відмов перевищує норму (напр., >5%).

## 3. План дій у випадку підозри на атаку (Runbook)

Якщо моніторинг виявив аномальну активність, слід виконати наступні кроки:

### Крок 1: Ідентифікація та підтвердження атаки

1.  **Перевірити кількість реєстрацій:** Виконайте SQL-запит з п. 2.1, щоб підтвердити аномальний сплеск.
2.  **Проаналізувати логи веб-сервера:** Перевірте логи на наявність великої кількості `POST` запитів до `/api/auth/register/` з однієї IP-адреси або підмережі.
3.  **Перевірити панель email-провайдера:** Оцініть поточний відсоток відмов та кількість надісланих листів.

### Крок 2: Негайне стримування атаки

1.  **Посилення троттлінгу:** Найшвидший спосіб — тимчасово зменшити ліміти запитів.
    - **Дія:** У файлі `backend/backend/settings.py` або відповідному `.env` файлі змініть значення, наприклад:
      ```python
      # Посилені налаштування
      COMMON_REDIS_THROTTLE_RATE = 2
      EMAIL_THROTTLE_RATE = 1
      ```
    - **Результат:** Це значно сповільнить атаку.

### Крок 3: Розслідування та очищення

1.  **Блокування зловмисних IP:** Якщо атака йде з обмеженого пулу IP-адрес, заблокуйте їх на рівні інфраструктури (файрвол, WAF, Nginx).
2.  **Аналіз та видалення фейкових акаунтів:**
    - **Дія:** Знайдіть та видаліть користувачів, створених під час атаки, які не верифікували свою пошту.
    - **Приклад запиту:**
      ```sql
      -- Знайти неактивних користувачів, створених під час атаки
      SELECT id, email, date_joined FROM users_user
      WHERE is_active = false AND date_joined BETWEEN 'YYYY-MM-DD HH:MI:SS' AND 'YYYY-MM-DD HH:MI:SS';

      -- (Після перевірки) Видалити їх
      -- DELETE FROM users_user WHERE id IN (...);
      ```

### Крок 4: Повернення до нормального режиму

Після того, як атака припинилася і наслідки усунуті, поверніть налаштування троттлінгу до стандартних значень.
